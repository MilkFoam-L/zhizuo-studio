# 每日任务额度与供应商核对

本模块限制每个工作空间每天提交的新生成任务数。一次图片任务或一次图文任务各占一次额度。单位是“次任务”，不是人民币、积分余额、供应商的 token 用量或实际付款金额；当前不能据此计算供应商费用、收入、退款或利润。供应商没有返回费用时，费用继续标记为未知。

## 日期与策略

- 日界线固定为 `Asia/Shanghai` 的 00:00，与服务器所在时区无关。
- 默认额度由创建 `QuotaService` 时的 `defaultLimit` 决定，构造器省略时为 100。第一次访问空间时持久化该空间的策略；修改默认值不会覆盖已保存的空间设置。
- 管理员可用 `setLimit` 修改某空间的每日额度，取值为 0 至 1,000,000 的整数。0 可阻止新的生成任务。
- 调整同时影响今天和未来新建的日期窗口，不修改历史日期窗口。新额度不能低于今天已消耗与预占的总和。
- 今天的剩余额度为 `limit - reserved - consumed`。待核对的任务仍计入其原始日期的 `reserved`。
- 午夜后为新一天建立窗口；跨午夜完成、取消或人工核对的任务结算到原预占日期，不占用新一天额度，也不增加新一天额度。

## 状态与处理

| 状态 | 含义 | 计数 |
| --- | --- | --- |
| `reserved` | 任务已创建，等待执行或正在执行 | 原窗口预占 +1 |
| `review` | 请求已尝试提交或供应商结果不确定，等待核对 | 继续保留原窗口预占 |
| `consumed` | 已成功生成，或管理员核对后确认使用 | 原窗口预占 -1，已使用 +1 |
| `released` | 确定尚未请求供应商，或管理员核对后恢复额度 | 原窗口预占 -1 |

任务成功时确认消耗；从 `review` 恢复查询成功时也可确认消耗。排队取消、明确在供应商请求开始前失败时释放额度。

任务记录含 `submissionStartedAt`、`submissionStarted: true` 或 `upstreamTaskId` 时，失败与取消保留额度并进入待核对。旧任务缺少这些字段且 `attempts > 0` 时也保守进入待核对。新任务应创建 `submissionStarted: false`，worker 在尝试发出请求前将其置为 `true` 并持久化时间。不要仅因没有上游任务编号就将已执行任务判断为未提交。

已进入 `review` 的任务不会因后续错误回调自动释放。成功、释放均为额度终态，重复结算不会重复扣减或恢复；旧回调不能覆盖人工核对结果。重复使用相同任务 ID 只返回原记录，不重新预占。如果用户确实新发起一次生成，必须创建新的任务 ID 并接受新的额度检查。

## 数据结构与事务

- `quota_policies`：每个工作空间的持续每日额度。
- `quota_windows`：每个空间、日期的额度、预占、已使用计数，数据库约束保证不为负且总数不超过额度。
- `quota_reservations`：以任务 ID 为唯一键，记录原空间、日期、状态与时间。保留终态记录以支持幂等。
- `quota_events`：业务代码只追加事件，包含空间、日期、任务、动作、前后状态或限额、原因、操作人和时间。核对与策略调整都会记录，服务不提供修改历史事件的入口。

支持 PostgreSQL 和本地 PGlite。所有写操作使用 `Database.transaction`；嵌套调用加入同一个调用者事务，并使用数据库行锁协调多个服务实例。容量检查与预占是受条件限制的数据库更新，不依赖进程内计数器。服务重启不会重建或清零已有窗口。

创建任务必须把额度预占与任务写入放在同一事务中：

```ts
await db.transaction(async () => {
  await quotas.reserve(task.id, workspaceId);
  await db.put('tasks', task.id, task);
});
```

任务状态变更与结算也应在同一数据库事务中完成，或在恢复过程中重放幂等结算。网络请求不应放在持有数据库事务锁的区间。

旧任务没有预占记录时，`settle` 不补扣额度，也不猜测历史费用。若导入项目备份，需要保留导入与新发起生成的区别，不能把历史版本当作新的计费任务。

## 服务接口与授权边界

| 方法 | 返回或行为 |
| --- | --- |
| `initialize()` | 幂等建表和索引 |
| `reserve(taskId, workspaceId)` | 返回预占记录；额度耗尽抛出 `QUOTA_EXCEEDED / 429`；同一任务跨空间使用返回冲突 |
| `settle(task)` | 返回更新后的记录；旧任务无预占时返回 `undefined` |
| `summary(workspaceId)` | 今天的 limit、reserved、consumed、available；整个空间的 reviewCount；最近 50 条预占记录和最近 50 条事件 |
| `reviewRecords(workspaceId, { cursor?, limit? })` | 按创建时间、任务 ID 升序分页返回该空间待核对记录；默认每页 25 条，最大 100 条；有后续数据时返回 nextCursor |
| `setLimit(workspaceId, limit, reason, actorId)` | 更新今天及未来每日策略，并返回该空间摘要 |
| `resolve(taskId, action, reason, actorId)` | action 为 consume 或 release，仅待核对记录可转换；同决策重试幂等，相反终态决策拒绝 |

`summary.reviewCount` 包含历史日期，前端应标注“待核对（含历史）”。其余计数仅为今天。事件和记录均按当前空间过滤，不从其他空间聚合。

管理员待核对列表使用 `reviewRecords`，因此历史待核对任务不会被摘要中的最近 50 条限制遮蔽。游标绑定空间、创建时间与任务 ID，并检查锚点归属；错误、篡改或借自其他空间的游标返回 400。处理完上一页的记录后仍可继续下一页，因为游标锚点允许已经核对的任务。游标不能替代空间授权。列表实时反映任务状态，已有任务稍后进入待核对时，刷新第一页可发现新变化；翻页采用稳定的创建时间，不会因已有记录的更新时间变化而重复显示。

服务类负责数据与额度约束，HTTP 路由负责认证、空间授权和管理员权限。不要直接信任客户端传入的 `workspaceId` 或 `actorId`。普通成员只能查看自身工作空间的摘要，限额配置和人工核对由管理员操作。

调用 `resolve` 前，路由必须在同一事务中锁定任务记录，校验该管理员有权处理此空间，并拒绝正在排队、执行或持有有效执行租约的任务。可恢复的任务必须先停止后续恢复，防止核对与 worker 继续查询并发。仅有额度记录的 `review` 状态不能证明对应 worker 已停止。

人工核对必须填写 1 至 500 字依据，例如“供应商后台已确认原任务未执行，恢复平台任务额度”。该操作只改变本产品的任务次数，没有向供应商申请退款，也没有撤销供应商账单。页面需要明确传达这一点。

## 验证入口

```sh
npx tsx --test apps/server/tests/quotas.test.ts
```

测试覆盖并发容量、重复预占、跨空间隔离、创建任务与预占同时回滚、成功与取消幂等结算、未知结果保留、人工核对竞争、每日限额调整、跨上海午夜、审计写入失败回滚、历史列表边界、超过 50 条历史待核对任务的完整分页、非法游标和数据库重启。当前单元测试默认运行 PGlite；真实 PostgreSQL 多连接、多 worker 与并发额度的验证证据见 POSTGRES-VALIDATION.md。真实供应商计费尚未验收，不能由任务额度测试推断。

## 备份与回退

额度表必须随数据库完整备份；仅导出项目 ZIP 不包含服务级额度策略与审计。回退应用代码时，不应删除额度表或将历史状态重置为 `reserved`。恢复数据库时同时恢复任务数据，保持任务与预占的一致性。

如果发现计数与预占不一致，停止该空间新任务，保存备份并逐项核对记录。不要自动把待核对任务全部释放，也不要用覆盖旧审计事件的方式“修正”供应商成本。
