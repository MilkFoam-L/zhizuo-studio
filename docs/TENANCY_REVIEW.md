# 账号隔离专项审阅

审阅日期：2026-09-30。范围为个人账号集成后的 `app.ts`、`accounts.ts`、`repository.ts`、`backup.ts`、`jobs.ts`。使用临时 PGlite、Fastify `inject` 和供应商函数替身核实；没有访问真实供应商或使用真实账号。下列两项发现均已修复，并通过 worker 与 HTTP 集成回归；保留修复前输出以说明触发条件。

## 发现 1：停用完成后，在途请求仍能排入收费任务

优先级：P1，已修复并回归。发现时，`preHandler` 只在请求进入时缓存会话；创建任务在另一个队列内等待，入队前没有重新核验账号。管理员停用账号并遍历取消现有任务后，一个已经通过 `preHandler` 的请求仍可能落库为 `queued`。执行器没有独立检查账号状态。

实证方法：暂时延迟创建任务的数据库 INSERT，在同一临时应用中调用管理员停用接口，等其返回后释放 INSERT；之后触发一次 worker tick，替身记录供应商调用数。

发现时输出：

```json
{
  "disableStatus": 200,
  "postDisableCreationStatus": 200,
  "createdStatus": "queued",
  "executionCallsAfterDisable": 1,
  "finalTaskStatus": "succeeded"
}
```

修复由两部分组成：任务创建和账号停用使用同一个应用级串行队列，并在进入该队列后重新核验会话；执行器领取任务前、读取参考图之后且调用供应商之前，分别检查 `canRunProject(projectId)`。检查失败将任务标为已取消，避免继续提交或恢复查询。

## 发现 2：切换认证模式后，无法查看的旧任务仍在执行

优先级：P1，已修复并回归。发现时，HTTP 资源已按工作空间隔离，但 worker 仍扫描所有任务。保留一个本地模式的排队任务后，将相同数据目录切换到账号模式，管理员无法列举原项目，也无法取消其任务，worker 却仍使用旧密钥执行任务。

发现时输出：

```json
{
  "visibleProjectsAfterSwitch": 0,
  "cancelOldTaskStatus": 404,
  "oldTaskExecutions": 1,
  "taskStatus": "succeeded"
}
```

应用层已提供模式相关的 `canRunProject`：本地/共享模式仅允许 `local` 工作空间；账号模式仅允许存在且启用的账号所属空间。worker 对不能执行的队列记录标为已取消，保留已有上游任务编号与费用核对说明。

资源归属本身不应因修改环境变量而隐式迁移。本地/共享项目升级为个人账号项目时，应通过备份导入明确创建新的归属；反向切换也应保留数据库和原始文件。该审阅不把「原项目从列表消失」当作数据已经迁移成功。

## 其余审阅结论

静态核对未发现现有路由绕过工作空间归属：项目/服务商路径由解析后的路由检查；素材、版本、任务路径追溯所属项目；导出显式检查项目；画布引用、海报素材、父版本、分镜来源都要求属于当前项目。备份导入丢弃原空间归属并使用服务端会话的空间，同时重映射素材和版本 ID。每日任务数和用量只统计当前空间所属项目。

已完成的是个人账号与所有者资源隔离；团队共享、邀请、账号恢复、付费结算和独立 worker 不在这些测试所证明的范围。浏览器工具仍因保存的权限策略拒绝本地页面，管理 UI 没有界面实测证据。PGlite 与注入式 HTTP 回归不证明多进程、分布式队列、真实 PostgreSQL、真实 S3 或真实模型接入。

旧记录缺失 workspaceId 时按 local 处理；切模式不自动变更归属。回退到 `cf84867` 必须恢复账号隔离前的数据备份，不能用旧版全空间读取代码访问新增的个人账号数据。操作说明见 `MIGRATIONS.md`。
