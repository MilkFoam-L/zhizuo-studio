# 服务端正确性审查与修复记录

审查日期：2026-09-30。范围：`app.ts`、`jobs.ts`、`db.ts`、`backup.ts`；为验证调用关系同时阅读了 `repository.ts`、`media.ts` 和 `validation.ts`。这是开发期间的审查记录，不代表真实供应商、云数据库或公网部署已经验收。

## P1：编码路径绕过登录保护

**位置**：`app.ts` 的 `onRequest` hook，原实现使用 `req.url.startsWith('/api/')` 判断是否鉴权。

**触发与证据**：Fastify 路由会解码路径中的字符，`/%61pi/projects` 被匹配到 `/api/projects`；原 hook 看到的 raw URL 不以 `/api/` 开头，直接跳过 session 检查。本次通过实际 Fastify `inject` 验证普通 `/api/projects` 返回 401，同一处理器的 `/%61pi/projects` 返回 200。部署访问密码模式时，没有 Origin 的外部 HTTP 客户端可以用这个路径访问项目、素材和付费任务接口。

**建议**：依据框架确定的 `req.routeOptions.url` 对 API 路由统一鉴权，或先可靠地解码并规范化 pathname；不要依据 raw URL 的字符串前缀决定鉴权。session/health 白名单和 Cache-Control 应采用相同判断。新增未登录请求 `/%61pi/projects`、`/%61pi/providers` 以及编码的任务提交路径回归测试。

**状态**：已向主代理立即报告，由主代理修复 `app.ts` 并做集成验证。

## P1：取消与结果发布存在竞态（已修复并验证）

**位置**：原 `jobs.ts` 的 `run()` 在查询取消状态后，单独调用 `repo.version()`，最后才条件更新任务为成功。

**触发**：生成结果已返回 → worker 检查任务未取消 → 取消请求写入 cancelled → worker 创建版本/画布节点 → succeeded 条件更新匹配不到任务。结果是取消状态与已发布版本同时存在。图片原本还在取消检查前保存，因此取消也会留下没有版本的图片资产。

**修复**：当前 `jobs.ts` 对 claim、cancel 和结果发布使用同一任务互斥锁。先赢得锁的取消会阻止保存素材和版本；已经进入发布的操作完成后，取消返回实际 succeeded 状态。没有提前伪造成功。约束为当前单个服务进程/单个 runner，不宣称跨进程互斥。

**验证**：`jobs.test.ts` 分别阻塞供应商完成与版本持久化，验证两个顺序；同时确认取消后素材与版本均未产生，发布完成后只产生一个版本和节点。

## P1：关闭服务时尚未结束的 tick 仍可提交任务（已修复并验证）

**位置**：原 `JobRunner.stop()` 只清定时器并等待当前 `running` 快照，未等待正在查询/领取任务的 tick。

**触发与证据**：在任务列表读取处挂起 tick，等待旧版 stop 返回，再释放读取，实测 `startedAfterStop: 1`。如果随后数据库已被 `onClose` 关闭，就可能发生关闭后请求供应商和写入失败。原定时器的 `void tick()` 也没有捕获数据库错误，会产生未处理拒绝。

**修复**：当前实现保存 tick promise 和停止标记，停止后拒绝新领取；已领取但尚未发送的任务恢复 queued，stop 等待 tick 和所有实际运行任务结束后才返回。定时轮询异常有固定、不含凭据的错误报告。

**验证**：`jobs.test.ts` 包含任务列表读取中停止、领取数据库响应中停止，以及轮询数据库失败三个场景。

## P1：并发创建任务可越过每日额度

**位置**：`app.ts` 创建任务时，原代码分开执行“读取全部任务并计数”和 INSERT。

**触发**：当剩余一个名额时，两个不同幂等 key 的请求同时读取到旧计数，随后都插入成功。任务主键的唯一约束可以防止同一个 key 重复插入，但不能保证不同 key 的额度原子性。

**建议**：当前单实例约束下，对额度判断和插入串行化；未来多进程采用数据库内的计数/额度预留事务。启动时验证 `MAX_DAILY_TASKS` 是正整数，避免 NaN 意外关闭限额。

**状态**：主代理已加入配置校验与单实例额度处理，仍应由其集成测试核实并发边界及同 key 重放。

## P2：ZIP 重复 ID、悬空引用造成静默数据丢失

**位置**：原 `backup.ts` 的 `restore()` 用 Map 重新映射 ID，却未验证唯一性、父版本和画布引用。

**触发与证据**：本次构造两个相同版本 ID 的合法 JSON 对象和一个引用缺失版本的节点，直接调用 restore 的隔离存储替身，输出为 `inputVersions: 2, restoredVersions: 1, missingNodeRefSilentlyDropped: true`。重复版本被后者覆盖，悬空引用被改成 undefined；未报错。

**建议**：在创建任何项目/文件之前验证素材、版本、节点、边的 ID 唯一；所有版本/素材引用存在；父版本无环；版本内容与 kind 一致。保留有效的创建时间和输入快照，并将快照内 `referenceAssetId` 同步映射为新 ID。

**状态**：主代理已添加唯一性、引用、父版本循环与历史字段校验/保留。建议其集成测试继续验证负例不会留下项目/文件。

## P2：导出成功的项目备份可能无法重新导入

**位置**：`backup.ts` 的导出只检查资产累计 100 MB，而导入另有限制：200 个素材、1000 个版本、5 MB project.json；`media.ts` 接受上传 24 MB、允许规范化 PNG 达 40 MB，但 restore 又按上传限制读取导出的 PNG。

**影响**：正常项目超过 200 个小素材或版本元数据超过 5 MB 仍可能下载出备份，恢复时才被拒绝。24–40 MB 的内部规范化 PNG 也可能无法通过恢复时的 `ingest()`。资产刚好接近 100 MB 时，加上 JSON 和 ZIP 开销，还可能超过上传文件的 100 MB 限制。

**建议**：统一导入与导出契约，导出前执行同一 schema/计数/元数据大小检查，压缩后也验证可上传大小。对受限且已校验的内部 PNG 备份使用明确的恢复大小上限，或者从源头收敛规范化资产上限。新增边界备份往返测试。

**状态**：已单独通知主代理，需核实最终实现。

## P2：局部持久化失败会留下文件/版本

**位置**：`Repository.version()` 先写版本，再追加画布节点；`Media.ingest()` 先写主图，再写缩略图，最后写资产记录。

**影响**：节点追加冲突/失败或写磁盘/数据库失败时，API 可以报失败但已经留下持久化对象。用户重试可能出现重复版本；只有文件但没有资产记录时，恢复逻辑也无法通过 `db.list('assets')` 找到文件进行清理。

**已在 jobs 修复**：任务生成后保存失败会清理本任务版本和节点，以及没有其他引用的生成资产；已成功提交但数据库响应丢失时，重新读取成功状态并保留结果。供应商已返回结果但本地保存失败，任务标为 reconciling 并提示可能已经计费。真实 PGlite 测试覆盖部分版本写入后失败、成功响应丢失和共享资产保护。

**仍需调用方处理**：`Media.ingest()` 应在自身失败路径清理自己创建的文件，因为失败时 runner 尚未收到 assetId；手工创建版本/上传素材 API 也需要失败补偿或持久化事务，不能只依赖任务 runner。已通知主代理。

## 其他具体事项

- `app.ts` 的 `Host.split(':')[0]` 把 `[::1]:4310` 解析为 `[`，与入口允许 `HOST=::1` 的设置不一致；应使用 URL/IPv6 感知解析，并加入 IPv6 loopback 注入测试。
- 全局错误处理器默认把未知数据库/文件错误作为 400 返回原始 message，会暴露本地路径并把服务端故障归为输入错误。建议将已知业务错误白名单化，未知错误返回通用 500，内部日志进行字段脱敏。
- 同一个 idempotencyKey 携带不同有效载荷时，当前会返回旧任务。建议保存原始请求指纹，不同参数复用同一 key 返回 409，避免旧结果被误认为新操作结果。
- 当前 `db.ts` 参数化查询和任务插入的 `(scope,id)` 唯一约束可以阻止重复主键；未发现这些路径存在字符串拼接 SQL 注入。
- 检查到 `publicProvider()` 去除 secret、`publicTask()` 去除 secret/config/brief、项目公开详情调用公开映射、ZIP 不包含 providers/tasks/sessions。在正常数据模型下没有发现明文供应商密钥被这些出口直接返回。此结论不覆盖未部署的日志平台或未来字段。
- ZIP 文件名白名单不会将外部路径写入磁盘；当前已有限制累计解压大小，但使用同步解压，会占用事件循环。服务公网化前应测量最大合法备份耗时与并发资源占用。
